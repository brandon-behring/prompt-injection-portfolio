# Research Plan: Agentic security architecture — agent harness + capability-based isolation + score fusion + activation-probe methodology

The agentic-side complement to `direct-vs-indirect/`: how agent-shaped systems (tool-calling loops with side effects) are defended via capability-based isolation (CaMeL, IsolateGPT/SecGPT, dual-LLM patterns), how multi-detector scores are fused into stacked classifiers (Meta PG2 Recall@1%FPR loss, embedding-based scorers, LogisticStacker), how activation-probe methods (TaskTracker, InstructDetector, AttentionTracker) work beyond softmax, and how the current agentic-bench layer (AgentDojo / LLMail-Inject / ASB / τ-Bench) is critiqued by 2025-26 saturation + adaptive-attack literature. Lane 4 + Lane 5 anchor; primary audience: future LLM agents picking up portfolio Lanes 4-5 + the user authoring Ch 11-12. Target ~20-25 primary-source entries across 5 sub-areas (Sprint 2 topic D).

## Sub-areas

- D1. Agent harness security architecture
  - Source types: arXiv, vendor engineering blog posts, NeurIPS/ICML/CCS/USENIX proceedings, framework docs (LangChain, AutoGen, OpenAI Assistants, Anthropic Claude Code, Cursor)
  - Notes: System-shape literature on tool-calling agents — what the agent harness actually is, why it differs from chat (multi-turn tool-call loops, side-effect surfaces, persistent memory, sub-agent delegation). LlamaFirewall (Meta arXiv 2505.03574) as the canonical "agent harness with layered guards" reference. AgentArmor (per compass §6) as agent-layer firewall pattern. ReAct / Function-calling / Toolformer lineage as foundational. Key claim: side effects are what makes agentic injection categorically worse than chat injection — same level of detection accuracy translates to vastly higher blast radius.

- D2. Capability-based isolation + dual-LLM patterns
  - Source types: arXiv preprints, conference proceedings (NDSS, S&P, USENIX), researcher blogs (Simon Willison)
  - Notes: CaMeL (Debenedetti, Shumailov, Fan, Hayes, Carlini, Fabian, Kern, Shi, Terzis, Tramèr — Google/DeepMind/ETH, arXiv 2503.18813 v1 + v2) — privileged-LLM / quarantined-LLM split with custom Python interpreter + capability tags on every value; 77% provably-secure on AgentDojo v2 (vs 84% undefended; was 67% in v1). IsolateGPT / SecGPT (Wu et al. NDSS 2025) — per-plugin sandboxing with orchestrator mediation. Willison "Dual LLM pattern" (April 2023 blog → April 2025 CaMeL analysis) — the canonical informal articulation; "original sin of LLMs… trusted prompts and untrusted text concatenated into the same token stream." Capability tags + provenance metadata as the structural primitive (vs content classification). Information-flow control descended from SLam/Jif/HiStar lineage. The token-cost / utility-cost tradeoff (CaMeL ~2.8× input / 2.7× output tokens). Distinct from `architectural_defense_methods` (`direct-vs-indirect/B2`) which is broader (Spotlighting / StruQ / SecAlign / Jatmo / Instruction Hierarchy live there); this sub-area is specifically about *capability-based + dual-LLM* isolation as a structural-typed-channel approach.

- D3. Score fusion + stacker theory
  - Source types: arXiv, vendor engineering blogs (Meta AI, CodeIntegrity), HuggingFace model cards, eval-toolkit release notes
  - Notes: The meta-learning layer on top of per-detector scores. Meta Prompt Guard 2 family's custom Recall@1%FPR loss (Meta model card; cited in PromptShield 2025 as basis for the "low-FPR collapse" reporting convention). Energy-based loss (Liu NeurIPS 2020 arXiv 2010.03759) as the foundation Meta + CodeIntegrity both use. Embedding-based detectors (Ayub & Majumdar arXiv 2410.22284) — XGBoost / Random Forest / MLP on OpenAI text-embedding-3-small space; treated here as a stacker-eligible signal class. LogisticStacker per eval-toolkit v0.47.0+ (portfolio's own stacker primitive per Lane 4). APR metric (Meta PG2 — % attacks blocked at ≤3% utility loss) as the score-fusion-relevant reporting unit. Ensemble methods for low-FPR operation: when single-detector AUC saturates, can correlated detectors deliver complementary signals? Lane 4's open question. Cross-link to `evaluation_metrics` + `training_methodologies` in `training-and-evaluation/` for upstream methodology context; this sub-area focuses on the *combination* layer.

- D4. Activation-probe methodology beyond TaskTracker
  - Source types: arXiv, IEEE SaTML proceedings, GitHub repos
  - Notes: The hidden-state signal class. TaskTracker (Abdelnabi et al. IEEE SaTML 2025 arXiv 2406.00799) — linear probe on activation deltas (pre- vs post-untrusted-data injection) on decoder LLMs; >0.99 AUC on synthetic task-drift, contested generalization on real adaptive attacks. InstructDetector (arXiv 2505.06311) — activation-based detector; 96.90% OOD accuracy on BIPIA, ASR 0.12%. AttentionTracker / hung2025 family (Hung et al. — paper TBD via /research-gather) — attention-head-level signal class. Linear-probe approaches on penultimate hidden states (768D ModernBERT, 4096D Llama-3.1-8B). Generalization gap: encoder vs decoder architectures, IDD vs OOD task drift, real-time inference cost (~1h GPU per slice extraction). Independent re-evaluations critiquing TaskTracker's benign-text-distribution-sharing between train and test. Lane 5's encoder-only port test — does the recipe transfer to ModernBERT activation space? Cross-link to `detector_architectures` in `detector-landscape/A5` for the broader specialized-detector landscape; this sub-area focuses specifically on the *activation-delta signal class methodology*.

- D5. Agentic-bench critique + adaptive evaluation
  - Source types: arXiv preprints (incl. critique papers), NeurIPS/ICML/IEEE SaTML proceedings, competition GitHub repos
  - Notes: The benchmark layer used to evaluate D1-D4 defenses. LlamaFirewall (arXiv 2505.03574 Meta) — layered agent firewall design + AgentDojo APR numbers. Task Shield (arXiv 2412.16682) — instruction-and-tool-call goal verification, 2.07% ASR / 69.79% utility on AgentDojo GPT-4o. MELON (Masked Re-Execution and Tool Comparison; arXiv 2502.05174 ICML 2025) — 0.24% ASR / 68.52% utility. AgentArmor — paper TBD via /research-gather; agent-layer firewall pattern. Bhagwatkar "Are Firewalls All You Need?" (NeurIPS 2025 arXiv 2510.05244) — saturation critique: AgentDojo / ASB / InjecAgent / τ-Bench saturated by two-firewall defenses; weak-attack pathologies hinder progress. LLMail-Inject (Microsoft IEEE SaTML 2025 arXiv 2506.09956) — 208K adaptive attacks from 839 participants — the current gold standard for adaptive eval. Nasr "Attacker moves second" (arXiv 2510.09023) — static-defense critique applied to agent harnesses. 2026 adaptive-attacker benchmarks (AgentDyn / AgentSentry / AgentVigil) cross-referenced from `agentic_benchmarks` in `direct-vs-indirect/B4`. Cross-link: the *agentic benchmarks themselves* (BIPIA, InjecAgent, AgentDojo, ASB, τ-Bench, LLMail-Inject) are catalogued in `direct-vs-indirect/B4` under `agentic_benchmarks`; this sub-area covers the *defenses-evaluated-on-them* + the *methodology critique* layer, not the benchmark catalogue.

## Out-of-scope

- Classifier-only detectors (encoder + LLM-as-judge + activation-probe-as-classifier) when evaluated only on text-classification benchmarks — covered comprehensively in `detector-landscape/A1-A5`. This dossier cites detectors only when they're (a) wired into an agent-harness stack (D1), (b) used as a per-row score input to a stacker (D3), or (c) re-evaluated on agentic benchmarks (D5).
- Pure threat-model taxonomies (Greshake / OWASP LLM01 / MITRE ATLAS) — covered in `direct-vs-indirect/B1` under `injection_threat_model`. This dossier cites them only as context for capability-tracking + dual-LLM motivation.
- Training-data catalogs + per-dataset analysis — covered in `training-and-evaluation/C1` under `training_data_sources`.
- Architectural defenses that aren't capability-based or dual-LLM-pattern (Spotlighting, StruQ, SecAlign, Jatmo, Instruction Hierarchy) — covered in `direct-vs-indirect/B2` under `architectural_defense_methods`. This dossier cites them only when they appear as a layer inside an agent harness (D1) or as a per-row signal in score fusion (D3).
- RAG-specific defenses (retrieval-time provenance, signed documents, RAG-poisoning detectors) — covered in `rag-injection-defenses/E` (Sprint 2 sister topic). The split is: D = agent harness + capability isolation + score fusion + activation probes + agentic-bench critique; E = RAG retrieval layer + document provenance + chunk-level defenses.
- Production incidents (EchoLeak, Month of AI Bugs, Slack AI, ShadowPrompt, etc.) — covered in `direct-vs-indirect/B3` under `production_incidents`. Cited here only when they motivate a specific capability-isolation or score-fusion design choice.
- Multimodal agentic injection (vision-language attacks on tool-using agents) — open research thread, no canonical taxonomy yet.
- Adversarial-suffix optimization attacks against the agent's backbone LLM (GCG / AutoDAN / PAIR) — they're attack benchmarks, not defense literature; cited as adaptive-attacker context only.

## Claim family taxonomy

Per ADR-007 domain-prefixed lowercase. Six families:

- `agent_harness_architecture` (NEW) — the system-shape layer: tool-calling agents, multi-turn loops, side-effect surfaces, sub-agent delegation, persistent memory. LlamaFirewall + AgentArmor + ReAct + Function-calling + Anthropic Claude Code + Cursor harness designs. Distinct from `architectural_defense_methods` which is *what the LLM does with text* (Spotlighting / StruQ / SecAlign); this family is *what the agent harness is shaped like* (the surface that capability isolation + score fusion + activation probes attach to).
- `agent_capability_isolation` (NEW) — capability-based + dual-LLM-pattern isolation specifically: CaMeL, IsolateGPT/SecGPT, Willison's dual-LLM, capability tags + provenance metadata, custom-interpreter approaches. Distinct from `architectural_defense_methods` (a broader bucket living in `direct-vs-indirect/B2` covering Spotlighting + StruQ + SecAlign + Jatmo + Instruction Hierarchy + CaMeL + IsolateGPT). Per validator: a single entry can declare exactly one `claim_family`; CaMeL + IsolateGPT will be classified under `agent_capability_isolation` here (the more specific family), and cross-referenced from `architectural_defense_methods` in `direct-vs-indirect/`.
- `dual_llm_pattern` (NEW) — narrowly the Willison 2023 dual-LLM articulation + its 2025 CaMeL formalization + its descendants. Separated from `agent_capability_isolation` because the dual-LLM pattern is a *historical + conceptual* claim (privileged-vs-quarantined; trust-boundary as the original sin) while capability-isolation is the *engineering* claim (tagging + interpreters). Keeps citation hygiene clean: Willison's informal blogs vs Debenedetti et al. formal paper.
- `score_fusion_stacker` (NEW) — the meta-learning layer: Recall@1%FPR loss (Meta PG2), energy-based loss (Liu NeurIPS 2020 — basis for both Meta PG2 + CodeIntegrity PromptGuard), embedding-based detectors (Ayub & Majumdar) as stacker-eligible signal, LogisticStacker (eval-toolkit v0.47.0+), APR metric for score-fusion-relevant reporting, ensemble methods for low-FPR operation.
- `activation_probe_methodology` (NEW) — the hidden-state signal class: TaskTracker linear-probe recipe + extensions; InstructDetector activation-based detector; AttentionTracker / hung2025 family; encoder vs decoder transfer questions; methodology critiques (benign-text-distribution sharing in TaskTracker's eval). Distinct from `detector_architectures` (which covers activation-probe-as-classifier among many shapes); this family is *the activation-delta signal class methodology specifically*.
- `agentic_bench_critique` (NEW) — the critique layer on top of `agentic_benchmarks` (which lives in `direct-vs-indirect/B4`): Bhagwatkar's saturation finding, weak-attack pathologies, LLMail-Inject as adaptive gold standard, Nasr "attacker moves second" applied to agents, 2026 adaptive-attacker benchmarks (AgentDyn / AgentSentry / AgentVigil) viewed as critique-vehicles for AgentDojo. The benchmarks themselves stay catalogued in `direct-vs-indirect/B4`; this family is *the methodology critique of those benchmarks*.

All six families are NEW (not in current glossary). Per ADR-007: glossary update is required in the same commit when these families first appear in `bib_ledger.yml` entries (enforced by `glossary_complete` test-contract).
